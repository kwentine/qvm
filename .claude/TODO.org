** Your INPUT chain does not cover forwarding
Packets get one of two paths through netfilter:
#+begin_example
  for the host itself:   prerouting → INPUT   → (local process)
  for someone else:      prerouting → FORWARD → postrouting
#+end_example
A packet from your LAN to a VM is /for someone else/: it never meets your =INPUT= chain.
Before today, the only =forward= chain was qvm0's, with =policy accept=. Example, from another machine on your wifi:
#+begin_src sh
  sudo ip route add 10.42.0.0/24 via <your laptop's LAN IP>
  ssh root@10.42.0.12      # reaches the VM: your INPUT drop policy is never consulted
#+end_src
Now covered by the =FORWARD= rule: =oifname "qvm0" iifname != "qvm0" ct state new drop=
(replies to connections the VMs opened are =established=, so they pass).
Your =INPUT= chain still matters, differently: allowing =qvm0= is what lets VMs reach dnsmasq (DHCP, DNS) on the host.

** Q: add the INPUT rule to the qvm0 table, to make it self-contained?
Not possible, and it is one of nftables' key rules ([[https://wiki.nftables.org/wiki-nftables/index.php/Configuring_chains][wiki: Configuring chains]]):
*a packet goes through every base chain on a hook, in priority order. =drop= is final, =accept= only ends the current chain.*
#+begin_example
  input hook:  inet kwentine INPUT (policy drop)  →  inet qvm0 INPUT (accept from qvm0)
               a DHCP request from a VM is dropped by the first chain; the second never sees it.
#+end_example
So an =accept= in our table cannot override your =drop=: the allowance must be in /your/ ruleset, as it is today.
Conversely, our =FORWARD= =drop= works whatever other tables say: that is why the hardening could live in =qvm0.nft=.
What we can do instead:
- Document it: "if your firewall drops input by default, allow DHCP and DNS from =qvm0=" (README, Phase 5).
- Narrow your rule, if you like: VMs only /need/ dnsmasq on the host:
  #+begin_src
    iifname "qvm0" udp dport { 53, 67 } accept
    iifname "qvm0" tcp dport 53 accept
  #+end_src
  Today =qvm0= in =allowed_interfaces= lets VMs reach every service on the host. Fine for a lab, your call.

** Tying =qvm-nat.service= to =nftables.service=
- *Problem*: Fedora's =nftables.service= runs =nft flush ruleset= on stop, and =flush ruleset; include …= on reload.
  "ruleset" means /every/ table, =inet qvm0= included. Typical trigger: you edit your =kwentine= table,
  =systemctl reload nftables=, and the VMs silently lose internet, while =qvm-nat.service= still says =active (exited)=.
- *Fix*, three directives in =[Unit]=:
  | Directive                               | Effect                                                            |
  |-----------------------------------------+-------------------------------------------------------------------|
  | =PartOf=nftables.service=               | stop/restart of nftables → stop/restart of qvm-nat               |
  | =ReloadPropagatedFrom=nftables.service= | reload of nftables → reload of qvm-nat (=ExecReload= loads the table again) |
  | =After=nftables.service=                | our table is loaded /after/ the flush, not before                 |
  On a host without =nftables.service=, they refer to a unit that never runs: no effect.
- *Demo*: [[file:../scratch/demo-nftables-coupling.sh]] (on your host, after install).

** Answer
- *Device units*: systemd tracks devices as units too. A udev rule (=99-systemd.rules=) tags every network interface,
  so when /anything/ creates =qvm0= (NetworkManager, =qvm-bridge=, a manual =ip link add=),
  =sys-subsystem-net-devices-qvm0.device= becomes active; when the interface disappears, it becomes inactive.
- *What dnsmasq needs is the interface, not its creator.* Before: =Requires=qvm-bridge.service=,
  which with NetworkManager would pull in the script bridge as well. The device unit is the common denominator.
- *The three dependency strengths*:
  | Directive   | Starting qvm-dns...         | If the device vanishes on its own (=nmcli con down=) |
  |-------------+-----------------------------+------------------------------------------------------|
  | =Wants==    | tries to start the device   | dnsmasq keeps running, serving a dead interface      |
  | =Requires== | needs it                    | same: Requires reacts to /stop jobs/, not to vanishing |
  | =BindsTo==  | needs it                    | *dnsmasq is stopped*                                 |
  =After== is separate: ordering only. With it, dnsmasq starts once =qvm0= exists, waiting up to 90 s for it.
- *=bind-dynamic=* covers the next gap: =qvm0= may exist before NetworkManager has given it =10.42.0.1=.
  =bind-interfaces= binds only the addresses present at startup (DHCP/DNS silently not served);
  =bind-dynamic= also binds addresses that appear later.
- *Not covered*: when =qvm0= comes back, dnsmasq does not restart by itself.
  Option: =WantedBy=sys-subsystem-net-devices-qvm0.device= in =[Install]= → dnsmasq starts whenever =qvm0= appears,
  including at boot since the NM profile autoconnects. Then =qvm-network.target= mostly matters for =qvm-nat=.
  - [X] Want that? → "No bridge at boot, only when I manually enable the connection."
- *Done* (2026-10-18): the bridge is the on/off switch.
  - Keyfile: =autoconnect=false=. =nmcli connection up qvm0= (no sudo in a desktop session) / =down=.
  - =qvm-dns= and =qvm-nat=: =WantedBy== and =BindsTo== the device → start when =qvm0= appears, stop when it goes.
