** Migrating your host
The old Makefile enabled *every* unit, including =qvm-bridge.service= and =qvm-machine-r0.service=.
Left enabled, =qvm-bridge.service= would delete NM's =qvm0= on stop. So:
#+begin_src sh
  sudo systemctl stop qvm-network.target
  sudo systemctl disable qvm-bridge.service qvm-machine-r0.service   # old leftovers
  sudo make uninstall && sudo make install
  sudo usermod -aG qvm "$USER"            # log in again
  # move your data from /var/vms to /var/opt/qvm/{templates,machines,localds,iso}
  # move user-data files to ~/.config/qvm/user-data/VM.yaml, machine configs to ~/.config/qvm/machines/VM
  sudo systemctl start qvm-network.target
#+end_src

| [[file:../scripts/qvm-run]]                     | *Random MAC each boot* + DHCP range of 11 addresses → new lease per boot, pool exhaustion, IP churn        |

I extendend the DHCP range, no reason to have it only 11.
I like the idea of deriving the MAC from the name. How would you go about it?
Ultimately, we should also allow the MAC to be configured in the TOML file.
- *Answer* (implemented in [[file:../scripts/qvm-run]]): =52:54:00= + the first 3 bytes of =sha256(VM name)=.
  #+begin_src sh
    hash="$(printf '%s' "${vm}" | sha256sum)"
    mac="52:54:00:${hash:0:2}:${hash:2:2}:${hash:4:2}"
  #+end_src
  - =52:54:00= is QEMU's own default prefix; its first byte has the "locally administered" bit set, so no clash with real hardware.
  - 24 bits from the hash: collision odds for 20 VMs ≈ 20²/2²⁵ ≈ 1 in 80 000.
  - dnsmasq also picks a client's address by hashing its MAC, so even after a lease expires the IP usually stays the same.
    To pin one: =dhcp-host=cp,10.42.0.10= in =dnsmasq.conf=.
  - =mac=…= in the machine config still overrides it; in TOML it becomes =mac = "52:54:00:…"=.
  - Later, multiple bridges: hash =bridge/name= instead, so the same VM name differs per bridge.

| [[file:../scripts/qvm-localds]]                 | needs =sudo mount= (breaks user services); tmp mountpoint never removed; reads =user-data/VM= (no =.yaml=) |

What is your proposed alternative? Could we do an =unshare= trick?
I liked the idea of a VFAT volume because it requires no extra tooling a la xorriso.
The tmp mountpoint is removed by the on_exit EXIT trap. Is that flawed?
You can go ahead and fix the `.yaml` inconsistency.
- *Done*: =.yaml= fixed.
- *Trap*: yes, flawed. =umount= does not remove the directory, so each run left an empty =/tmp/qvm-localds-XXXX=.
  Fixed with =rmdir= in =on_exit=.
- *unshare*: no. A user namespace lets you mount only filesystems marked safe for it (tmpfs, overlay, proc, FUSE…).
  vfat is a block-device filesystem: mounting it needs =CAP_SYS_ADMIN= in the /initial/ namespace, i.e. real root.
- *Proposal: let QEMU make the VFAT disk itself* (its =vvfat= driver). Write =user-data= and =meta-data= to
  =/var/opt/qvm/localds/VM/= as plain files, and attach the directory:
  #+begin_src sh
    -drive if=virtio,format=raw,read-only=on,file.driver=vvfat,file.dir=/var/opt/qvm/localds/VM,file.label=CIDATA
  #+end_src
  - Still VFAT, zero extra tooling (not even =mkfs.vfat=), no root, no image file, no mount.
  - Checked here with qemu 10.2 (Fedora 44): the guest sees a partition with =LABEL=CIDATA TYPE=vfat=,
    long file names intact — what cloud-init's NoCloud looks for. Not yet booted with a real cloud image.
  - Caveats: vvfat is "experimental" in read-write mode (we use read-only); RHEL builds of qemu disable it (your host is Fedora).
  - =qvm-localds= shrinks to =envsubst= + =cat >meta-data=.
  - Fallback if vvfat ever disappoints: =mcopy= from mtools writes into a vfat image without mounting.
  - [ ] Go ahead with vvfat?

| [[file:../systemd/qvm-nat.service]]             | =ExecStopPost= sets =ip_forward=0= globally: breaks podman/libvirt/docker if they run                      |
I never encountered any issues with podman, that I mostly run rootless. In what cases can this be a problem?
I introduced this because on my system ip_forward=0 by default?
What are our alternatives? Just not turning it off afterwards?
- *Why rootless podman never noticed*: it uses userspace networking (pasta/slirp4netns), not kernel forwarding.
- *Who breaks*: anything routing through the host kernel: rootful podman/docker, libvirt (=virbr0=),
  NetworkManager "shared" connections, WireGuard/Tailscale exit nodes. They turn forwarding on when they start;
  stopping qvm-nat later turns it off under their feet, and their guests lose connectivity silently.
- *Default*: yes, the kernel defaults to =0= and Fedora keeps it, so turning it on is needed.
- *Alternatives*:
  1. Turn on, never off (recommended): =/etc/sysctl.d/90-qvm.conf= with =net.ipv4.ip_forward = 1=, installed by make.
  2. Save the previous value on start, restore it on stop: fragile when several tools do the same.
  3. Per-interface =net.ipv4.conf.qvm0.forwarding=: does not suffice, replies arrive on the uplink (wifi/ethernet), which needs it too.
- *Side effect to know*: with forwarding on and no forward filtering, a machine on your LAN that uses your laptop as gateway
  could reach the VMs. Cheap hardening in =qvm0.nft=: in =FORWARD=, drop new connections /into/ =qvm0= that do not come from =qvm0=.
- Also pending here: tie =qvm-nat.service= to =nftables.service=, whose reload flushes the =qvm0= table (see PLAN.org Host facts).
  - [ ] OK for option 1 + hardening + nftables coupling?
