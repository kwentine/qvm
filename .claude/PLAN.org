#+TITLE: QVM — review and plan
#+STARTUP: overview
#+DATE: 2026-10-17

* Executive summary
- The core idea is sound and teaches a lot: *bridge + dnsmasq + nft + qemu + cloud-init*,
  with no libvirt in the way. Keep it that way: transparency is the product.
- The main structural problem is a *privilege split that isn't drawn yet*:
  scripts, Makefile and units mix root/system concerns with user/VM concerns
  (e.g. =make install= writes to =$HOME= and =/etc= alike; =qvm-localds= needs =sudo=; disks in =/var/opt=).
- Proposed shape:
  - *Host side (root, once)*: declarative config files only. No qvm executables needed.
  - *Machine side (user, daily)*: one unprivileged =qvm= CLI + =systemd --user= template units.
- Scope (decided 2026-10-17): side experiments (=fedora/ k8s/ rhel/ rke2/ scripts/{certs,bootc}=)
  are *lumber*, out of scope. Core = network + machines + install.
- Install layout (decided 2026-10-17): FHS =/opt= layout + =systemctl link=, kept.

* Feedback on the current state
** Strengths
- Small, readable bash with consistent conventions (=libqvm.sh=, self-documenting =#+= usage, dry-run).
- Good choices: qcow2 overlays with relative backing paths, NoCloud seed, =qemu-bridge-helper=-style
  =-nic bridge=, dedicated nft table (easy to flush), dnsmasq hostname→DNS registration.
- shellcheck/shfmt pre-commit already in place.

** Design issues (the real work)
1. *User units can't depend on system units.* =systemctl --user start qvm-machine@x= cannot be
   =After=qvm-network.target= (different managers). Need an =ExecStartPre= check, or simply
   enable the network at boot.
2. *Stopping a VM = pulling the plug.* systemd SIGTERMs qemu. Needs a QMP socket and
   =system_powerdown= in =ExecStop=, with a =TimeoutStopSec=.
3. *Undocumented prerequisite*: =-nic bridge= as a user needs =allow qvm0= in =/etc/qemu/bridge.conf=.
4. *Machine config is sourced bash* (=~/.config/qvm/machines/NAME=): arbitrary code execution,
   no validation. A small TOML file is safer and more explicit.
5. *Unit generation*: no need for a generator — a template unit =qvm-machine@.service= (=%i=) does it.
6. *=/opt= + =systemctl link=* (kept, it is FHS-coherent: =/opt/qvm=, =/etc/opt/qvm=, =/var/opt/qvm=). Caveats to respect:
   - linked files must live on the root fs (true for =/etc/opt=); =systemctl disable= also removes the link.
   - =systemctl enable /path= = link + enable; =qvm-network.target= has no =[Install]= → warning, harmless.
   - templates link fine: =systemctl --user link …/qvm-machine@.service=, then enable instances by name.
   - customise via drop-ins (=systemctl edit unit=) rather than editing the linked file.
   - user units: =systemctl --user link= is per-user, so it belongs in a separate, non-sudo =make= target.
7. +Firewalld interplay+ → not applicable: host runs =nftables.service= (see Host facts).

* Host facts: Fedora Atomic Sericea + =nftables.service= (2026-10-17)
- *=/opt= is a symlink to =/var/opt=* ([[https://docs.fedoraproject.org/en-US/atomic-desktops/technical-information/][Atomic docs]]):
  =/opt/qvm= and =/var/opt/qvm= are *the same directory*. Consequences:
  - code and data share one tree: keep subdirs disjoint (=bin/ venv/= vs =images/ machines/ seeds/=);
  - =make uninstall= must remove files by name, *never* =rm -rf /opt/qvm= (it holds the disks);
  - =/etc= is writable (3-way merged on upgrades): =/etc/opt/qvm=, NM keyfile, =/etc/qemu= are fine;
  - =groupadd qvm= lands in =/etc/group=: fine (the nss-altfiles gotcha only hits groups in =/usr/lib/group=).
- qemu is layered with rpm-ostree, so =/usr/libexec/qemu-bridge-helper= is setuid from the package: to verify.
- *=nftables.service= flushes the whole ruleset* on stop and reload (=flush ruleset= then re-include),
  which silently wipes the =qvm0= table. Fix in =qvm-nat.service=:
  =After=nftables.service=, =PartOf=nftables.service= (restart propagates),
  =ReloadPropagatedFrom=nftables.service= + =ExecReload=nft -f …= (reload propagates).
  Alternative: =include "/etc/opt/qvm/qvm0.nft"= in =/etc/sysconfig/nftables.conf= (edits a distro file).
  Also check your own ruleset: a =forward= chain with =policy drop= would need an accept for =qvm0=.
- =ip_forward=: set once in =/etc/sysctl.d/90-qvm.conf=, never reset to 0 on stop.

* Target architecture
** Privilege split
| Side    | Who / when          | What                                                     | Installed by                     |
|---------+---------------------+----------------------------------------------------------+----------------------------------|
| Host    | root, once          | bridge, DNS routing, NAT, dnsmasq, =bridge.conf=         | =sudo make install= (files only) |
| Machine | user, every day     | disks, seeds, qemu processes, ssh config                 | =make install-user= (no sudo)    |

** Locations
| Kind                     | Location                                                        |
|--------------------------+-----------------------------------------------------------------|
| Host config              | =/etc/opt/qvm/{dnsmasq.conf,qvm0.nft}=                           |
| Bridge + per-link DNS    | NetworkManager keyfile =/etc/NetworkManager/system-connections/qvm0.nmconnection= |
| System units             | =/etc/opt/qvm/systemd/qvm-*.{service,target}=, =systemctl link=ed |
| qemu bridge permission   | =/etc/qemu/bridge.conf=: =allow qvm0=                           |
| qvm CLI                  | venv in =/opt/qvm/venv=, =/opt/qvm/bin/qvm= → =../venv/bin/qvm=  |
| Bash helpers (kept)      | =/opt/qvm/bin/qvm-{bridge,create,localds,run}= (educational reference) |
| User units               | shipped: =/etc/opt/qvm/systemd/user/qvm-machine@.service=, =systemctl --user link=ed; yours (clusters): =~/.config/qvm/systemd/=, linked too |
| Machine/user-data config | =~/.config/qvm/{machines/NAME.toml,user-data/NAME.yaml}=        |
| SSH                      | =~/.config/qvm/ssh/{config,id_ed25519,known_hosts}=             |
| Disks, base images, seeds| =/var/opt/qvm/{images,machines,seeds}=, group =qvm=, setgid =2775= (only data location) |
| Runtime (QMP, serial)    | =$XDG_RUNTIME_DIR/qvm/NAME/=                                    |

** Replacing =resolvectl= with configuration (TODO in =qvm-dns.service=)
Per-link DNS can't be set in a =resolved.conf.d= drop-in; the link's owner must push it.
Decided: NM keyfile by default, scripts kept as the educational "manual way".
Draft: [[file:../config/qvm0.nmconnection]] — each setting annotated with the =ip=/=resolvectl= command it replaces.
Notable: NM enables STP by default (15 s forwarding delay on new VM taps) → =stp=false=.
Options considered:
1. *NetworkManager keyfile* for =qvm0= (Fedora already runs NM): bridge, static address,
   =dns=10.42.0.1=, =dns-search=~qvm0.lan;~qvm.lan;=, never-default. Replaces =qvm-bridge= *and* the resolvectl calls.
2. *systemd-networkd* =.netdev= + =.network=: same, plus =IPMasquerade== replaces the nft unit too.
   But it means running networkd next to NM (NM must ignore qvm0). Elegant, more moving parts.
3. Keep scripts + =resolvectl=: most explicit/educational, least idiomatic.
Keep dnsmasq and the nft table explicit in all cases — they are the interesting bits.

** Machine lifecycle (user units)
#+begin_src ini
# qvm-machine@.service (sketch)
[Service]
Type=exec
ExecStartPre=qvm check-host            # bridge exists? clear error otherwise
ExecStart=qvm run %i                    # foreground qemu, QMP socket in $XDG_RUNTIME_DIR/qvm/%i
ExecStartPost=qvm wait %i --timeout 120 # readiness probe: sshd answers
ExecStop=qvm stop %i                    # QMP system_powerdown, wait
TimeoutStopSec=90
#+end_src
Cluster = a plain target you write: =k8s.target= with =Wants=qvm-machine@cp.service …=.
